1. What is SIDEQUEST?

SIDEQUEST is a web platform where university students can find teammates and build projects together. It wraps this collaboration in a fun, game-like theme:

  • Quests = projects that need teammates
  • Guilds = communities/groups of students
  • Skill Trees = hierarchical skill categories students can level up in
  • Badges & Achievements = visual rewards shown on profiles
  • Player Cards = student profile cards styled like RPG character cards

A student posts a project ("quest"), defines open team roles with the skills required for each role, and other students browse the quest feed and apply to the roles that match their skills. Project owners review applications and accept or reject them.

2. How It Works (User Journey)

  1. Sign up — a student registers with email, password, full name, major, and college year.
  2. Build profile — they add skills from the skill tree and pick a rank tier (Bronze → Silver → Gold → Platinum → Diamond).
  3. Browse quests — the home feed shows open projects. Students can filter by skill, search by keyword, or filter by project status.
  4. Create a quest — a student can post their own project, describing it and listing open roles (e.g., "Frontend Developer × 2, needs React").
  5. Apply — another student applies to an open role. One application per role per person.
  6. Review — the project owner sees all applicants (with their skills and profiles) and accepts or rejects each one.
  7. Team up — accepted applicants become team members. When every spot across all roles is filled, the project automatically moves from OPEN to IN_PROGRESS.

Error handling

  • UnauthorizedAccessException → HTTP 403 when access isn't allowed

7. Backend — Security & Authentication

Registration & Login Flow

  1. User submits email + password (register also includes name, major, year).
  2. Passwords are hashed with BCrypt before storage — never saved as plain text.
  3. Emails are normalized to lowercase; duplicates are rejected.
  4. On successful login, Spring's AuthenticationManager verifies credentials.
  5. The server issues a signed JWT token valid for 24 hours containing the user's ID and email.

How protected endpoints work

  1. Every request passes through JwtAuthenticationFilter.
  2. The filter reads the Authorization: Bearer <token> header.
  3. The token signature is verified against the server's secret key.
  4. If valid, the user is authenticated for that request; otherwise the endpoint returns 401/403.
  5. CurrentUserService gives services easy access to "who is logged in".

What is public vs. protected

AccessEndpoints
Public (no token)Register, login, GET projects, GET skills
Authenticated (token required)Profile read/update, create project, apply, manage applications, add skills
Dev-onlyH2 console (only active with the dev profile)
CORS: the API only accepts browser requests from whitelisted origins (default: http://localhost:3000). Change it with the CORS_ALLOWED_ORIGINS environment variable.

9. Business Rules & Application Lifecycle

Rules enforced when applying to a role

  • The project must be in OPEN status
  • You cannot apply to your own project
  • You can apply to each role only once
  • The role must have spots remaining

Application state machine

            owner accepts            owner rejects
 PENDING ───────────────► ACCEPTED ─────────────► REJECTED
    │                                                 ▲
    └──────────── applicant withdraws ─────────────────┘

Concurrency safety

When someone applies or an owner decides on an application, the system places a pessimistic database lock on the role row before counting accepted members. This means two people applying at the exact same moment can never over-fill a role — one waits briefly for the other to finish.

Automatic project status changes

EventEffect on project status
Last available spot is acceptedOPEN → IN_PROGRESS (only when ALL roles are fully staffed)
An accepted member is rejected/withdrawn laterIN_PROGRESS → OPEN (others can apply again)

Data integrity guarantees

  • Passwords stored only as BCrypt hashes
  • Emails are unique and case-insensitive
  • Deleting a user removes their profile, skills, and applications (cascade)
  • A project owner cannot be deleted while their projects exist (restrict)
  • Skills referenced by roles or users cannot be accidentally deleted (restrict)

12. Running the Project Locally

Prerequisites

  • Java 17+, Node.js 18+, Maven (or use the included wrapper)
  • PostgreSQL only if you want persistent data (dev mode needs nothing)

Step 1 — Start the backend (dev mode)

cd backend
./mvnw spring-boot:run
# Runs on http://localhost:8080 with in-memory H2 database
# H2 console: http://localhost:8080/h2-console

Step 2 — Run the database schema (optional, for PostgreSQL)

createdb sidequest
psql -d sidequest -f ../database/schema.sql

Step 3 — Start the frontend

cd frontend
npm install
npm run dev
# Opens on http://localhost:3000

Step 4 — Run the backend tests

cd backend
./mvnw test

13. Recent Security Improvements

The following hardening changes were applied during review (August 2026):

  1. CORS locked down — was open to all origins with credentials; now restricted to whitelisted origins (default localhost:3000 only).
  2. JWT secret fail-fast — the app validates at startup that the secret exists and is ≥ 32 bytes; no more silent insecure default in production.
  3. H2 console isolated — only reachable under the dev profile.
  4. Race condition fixed — pessimistic row locks prevent over-filling roles under concurrent applications/decisions.
  5. Smarter project status — projects go IN_PROGRESS only when fully staffed, and reopen when a member leaves.
  6. Ownership check hardened — viewing applicants now verifies ownership explicitly, even with zero applications.
  7. Schema drift prevented — production uses ddl-auto: validate instead of auto-updating the schema.
  8. Typed API layer — all frontend API responses have TypeScript interfaces instead of any.

14. Known Limitations & Roadmap

Current limitations

  • No pagination yet — very large lists of projects/applications would slow down
  • JWT tokens live 24 hours with no refresh-token flow or logout revocation
  • Skill verification statuses exist in the data model but no verification process runs yet
  • No notifications — applicants aren't told when they're accepted/rejected
  • Token is stored in localStorage, which is readable by scripts if XSS ever occurred
  • Some home-feed content is mock/demo data mixed with real data

Suggested next steps (in priority order)

  1. Flyway migrations — version-controlled schema changes instead of manual SQL
  2. Refresh tokens + logout — short-lived access tokens, revocable sessions
  3. Pagination — for project listings and application lists
  4. Skill verification — peer endorsement or GitHub-based proof of skills
  5. Notifications — email or in-app alerts on application decisions
  6. More tests — cover the application state machine and permission rules
